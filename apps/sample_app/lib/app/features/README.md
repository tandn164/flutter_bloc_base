# App feature wiring

Each feature owns one folder. Keep dependency registration separate from route
composition; do not add a feature manifest or a combined `*_feature.dart` facade.

```text
features/
  onboarding/
    onboarding_di.dart
    onboarding_di.config.dart
    onboarding_routes.dart
    onboarding_routes.g.dart
  sample/
    sample_di.dart
    sample_di.config.dart    # generated by Injectable
    sample_routes.dart
    sample_routes.g.dart     # generated by go_router_builder
  showcase/
    showcase_routes.dart
    showcase_routes.g.dart
```

## Connect a feature

1. Import `<name>/<name>_di.dart` in app `di.dart` and call
   `await register<Name>Dependencies(sl)` after registering its shared dependencies.
2. Import `<name>/<name>_routes.dart` in `router/app_router.dart` and select its
   public routes or shell branch. Keep tab destinations in `app_shell.dart`
   aligned with the branch order.
3. Run `make codegen APP=sample_app` after changing generated DI or typed routes.
   Never edit generated companions by hand.

`make new-feature NAME=orders APP=sample_app` creates this layout and performs
the first two wiring steps. `make delete-feature NAME=orders APP=sample_app`
removes the scaffold-owned files and registrations after confirmation.

## Optional files are intentional

The same ownership and naming rules apply to every feature; their file counts
need not be identical. Showcase uses app-level services and registers no feature
dependencies, so it has no empty DI initializer. Both Onboarding and Sample use
Injectable and have a `.config.dart` companion, just like new scaffolded features.
All three features and new scaffolded features use typed routes with `.g.dart`
companions. Only annotation declarations contain static URL strings; navigation
uses generated helpers or locations. External deep-link payloads remain strings.

The app selects public routes and shell branches explicitly. Their static paths
come from typed locations, and page builders retain the supplied GetIt container.
Do not also mount a feature's generated `$appRoutes` list: that would duplicate
routes and could put tab routes outside the shell. For parameterized routes,
mount the generated route tree instead of using a concrete location as a pattern.

Reusable domain/data/presentation code stays in workspace `features/`; these
folders only connect that code to this app. Route files must not register DI,
and DI files must not import page builders or route definitions.

## One DI convention

Internal bindings belong in each package's `lib/di/` and are generated from class
annotations, including Domain use cases. App feature `*_di.dart` files only select
package modules; they do not repeat constructor bindings. Keep
`includeMicroPackages: false` to prevent unrelated features from registering.

Bootstrap awaits each selected initializer. Sample BLoCs are package-registered
factories; page callbacks resolve them and BlocProvider owns their disposal.
Onboarding has no BLoC dependency to register in Presentation. Showcase uses only
app services and therefore has no DI module.

The default `local` environment selects package repositories. For a custom
repository, register the contract first and use `environment: 'custom'`.
See the [DI guide](../../../../../tool/DEPENDENCY_INJECTION.md) for examples,
package layout, external contracts and lifetime rules.
